# Research note — Session 1: motivating Git for beginners

Verified 2026-09-14 against live sources (WebFetch + curl; PDF text extracted with pdftotext; kernel line count done locally on the 7.2 tarball). Status legend: VERIFIED / UNVERIFIED / WRONG.

Scope: how the reference courses *sell* Git before teaching commands, reusable numbers and stories, how they introduce branches as a concept, and three candidate 2h structures for the economics room (low bar: init/status/add/commit/log + push/pull; branches instructor-demo only). Companion to `research/s1-git.md` (commands, auth risks) — nothing there is repeated here.

## 2. How the reference courses motivate Git

Ordering key: **S** = solo first, **C** = collaboration first.

### 2.1 Software Carpentry, "Version Control with Git", ep. 1 "Automated Version Control" — **S then C**
Question: "What is version control and why should I use it?" Teaching time: 5 min (front matter `teaching: 5`). First image: the PhD comic. First sentence: "We'll start by exploring how version control can be used to keep track of what one person did and when. Even if you aren't collaborating with other people, automated version control is much better than this situation:" [comic] "We've all been in this situation before: it seems unnecessary to have multiple nearly-identical versions of the same document." Then the play-changes / versions / merge diagrams. Key points: "Version control is like an unlimited 'undo'." / "Version control also allows many people to work in parallel."
Instructor notes: "Version control might be the most important topic we teach, but Git is definitely the most complicated tool." "Because of this complexity, we don't teach novice learners about many interesting topics, such as branching, hashes, and commit objects. Instead we try to convince them that version control is useful for researchers working in teams or not, because it is — a better way to 'undo' changes, — a better way to collaborate than mailing files back and forth, and — a better way to share your code and other scientific work with the world." Opening trick: "Ask, 'Who uses "undo" in their editor?' All say 'Me'. 'Undo' is the simplest form of version control." Published minutes per episode (`teaching:`): 1 basics 5 · 2 setup 5 · 3 create 10 · 4 changes 20 · 5 history 25 · 6 ignore 5 · 7 remotes in GitHub 45 · 8 collaborating 25 · 9 conflicts 15 · 10 open science 5+5 · 11 licensing 5 · 12 citation 2 · 13 hosting 10 (≈ 3h to the first push, with ep. 7 alone at 45 min). Sources: https://swcarpentry.github.io/git-novice/01-basics.html , https://swcarpentry.github.io/git-novice/instructor/instructor-notes.html , front matter in https://github.com/swcarpentry/git-novice/tree/main/episodes . VERIFIED.

### 2.2 Pro Git ch. 1 — **S then C, via history**
"Version control is a system that records changes to a file or set of files over time so that you can recall specific versions later." Payoff list (solo first): "It allows you to revert selected files back to a previous state, revert the entire project back to a previous state, compare changes over time, see who last modified something that might be causing a problem, who introduced an issue and when, and more." Then the local → centralized → distributed story; the DVCS line is the one to reuse: "if any server dies … any of the client repositories can be copied back up to the server to restore it." https://git-scm.com/book/en/v2/Getting-Started-About-Version-Control . VERIFIED.

### 2.3 MIT Missing Semester, "Version Control (Git)" — **S then C, then data model bottom-up**
Opening: "Why is version control useful? Even when you're working by yourself, it can let you look at old snapshots of a project, keep a log of why certain changes were made, work on parallel branches of development, and much more. When working with others, it's an invaluable tool for seeing what other people have changed, as well as resolving conflicts in concurrent development." Then the audit questions: "Who wrote this module? When was this particular line of this particular file edited? By whom? Why was it edited?" The pedagogical thesis: "Because Git's interface is a leaky abstraction, learning Git top-down (starting with its interface / command-line interface) can lead to a lot of confusion. … While Git admittedly has an ugly interface, its underlying design and ideas are beautiful. While an ugly interface has to be *memorized*, a beautiful design can be *understood*. For this reason, we give a bottom-up explanation of Git, starting with its data model and later covering the command-line interface." Section order: data model → staging area → CLI → advanced → misc. One lecture slot; video length UNVERIFIED (~1h20 from memory). The 2026 edition still lists "Version Control and Git" as lecture 5 of 9 (and now has an "Agentic Coding" lecture). https://missing.csail.mit.edu/2020/version-control/ , https://missing.csail.mit.edu/ . VERIFIED.

### 2.4 GitHub Skills, "Introduction to GitHub" — **C only (GitHub-first)**
Under one hour; audience "new developers, new GitHub users, students"; steps: create a branch → commit a file → open a pull request → merge your pull request. Motivation is one line: "People use GitHub to build some of the most advanced technologies in the world." No solo argument, no terminal. https://github.com/skills/introduction-to-github . VERIFIED.

### 2.5 Julia Evans / Katie Sylor-Miller — motivation by *fear removal*
Oh Shit, Git!?! (Sylor-Miller, © 2016–2025) opens: "Git is hard: screwing up is easy, and figuring out how to fix your mistakes is fucking impossible. Git documentation has this chicken and egg problem where you can't search for how to get yourself out of a mess, unless you already know the name of the thing you need to know about in order to fix your problem." First scenario: "Oh shit, I did something terribly wrong, please tell me git has a magic time machine!?!" (reflog). https://ohshitgit.com/ . Evans's zine *How Git Works* (wizardzines.com/zines/git/) sells "commits! branches! merging! remotes!" and the promise that once you understand the design you can "recover lost commits". Her post "Confusing git terminology" (2023-11-01, https://jvns.ca/blog/2023/11/01/confusing-git-terminology/) is the list of words **not** to use on slide 1 (HEAD, detached HEAD, index/staged/cached, reset/revert/restore, tree-ish…). VERIFIED.

### 2.6 Learn Git Branching — **no motivation at all; model first**
Intro sequence: `intro/commits` → `intro/branching` → `intro/merging` → `intro/rebasing`. Level 1 text: "A commit in a git repository records a snapshot of all the (tracked) files in your directory. It's like a giant copy and paste, but even better!" … "for now you can think of commits as snapshots of the project." https://learngitbranching.js.org/ , source https://github.com/pcottle/learnGitBranching/tree/main/src/levels/intro . VERIFIED.

### 2.7 Happy Git and GitHub for the useR, ch. 1 "Why Git? Why GitHub?" (Jenny Bryan) — **C explicitly ranked above S**
"Git is a version control system. Its original purpose was to help groups of developers work collaboratively on big software projects. … If you have no idea what I'm talking about, think of it as the 'Track Changes' features from Microsoft Word on steroids." Then the honest ranking: "A solo data analyst, working on a single computer, will benefit from adopting version control. But not nearly enough to justify the pain of installation and workflow upheaval. There are much easier ways to get versioned back ups of your files, if that's all you're worried about. In my opinion, for new users, the pros of Git only outweigh the cons when you factor in the overhead of communicating and collaborating with other people. Who among us does not need to do that?" On GitHub: "think of it as DropBox but much, much better … Even for private solo projects, it's a good idea to push your work to a remote location for peace of mind." Sections: 1.1 Why Git? · 1.2 Why GitHub? · 1.3 Is it going to hurt? ("Yes.") · 1.4 What is the payoff? (Exposure, …) · 1.5 Who can do what? https://happygitwithr.com/big-picture . VERIFIED. The TAS paper (2.1 table row) is the same argument in article form.

### 2.8 Coursera / Udacity / Codecademy
Not checked (paywalled or login-gated syllabi); nothing here depends on them.

**Pattern across the courses.** Researcher-facing courses (SWC, Pro Git, Missing Semester) open SOLO with "unlimited undo" and *only then* collaboration; Bryan, writing for data analysts, says the opposite out loud: solo undo alone does not pay for the pain, collaboration does. GitHub Skills skips motivation. For this course the honest line is Bryan's plus the agent twist: the "collaborator" whose changes you must audit in Session 4 is the coding agent — which turns the SOLO case into a collaboration case on day one.

## 3. How the reference courses introduce branches as a concept

Teacher's framing: "there is a main/production branch that powers the live app; you cannot work directly on what is in production, so features and fixes happen on a separate branch and are merged back when ready." The sources below support that framing almost word for word.

- **Pro Git §3.1 "Branches in a Nutshell"** — "Branching means you diverge from the main line of development and continue to do work without messing with that main line." "A branch in Git is simply a lightweight movable pointer to one of these commits." "The 'master' branch in Git is not a special branch. It is exactly like any other branch." https://git-scm.com/book/en/v2/Git-Branching-Branches-in-a-Nutshell . VERIFIED.
- **Pro Git §3.2 "Basic Branching and Merging" — the hotfix story (quote on the slide).** "Let's go through a simple example of branching and merging with a workflow that you might use in the real world. You'll follow these steps: 1. Do some work on a website. 2. Create a branch for a new user story you're working on. 3. Do some work in that branch. At this stage, you'll receive a call that another issue is critical and you need a hotfix. You'll do the following: 1. Switch to your production branch. 2. Create a branch to add the hotfix. 3. After it's tested, merge the hotfix branch, and push to production. 4. Switch back to your original user story and continue working." Then: "Now you get the call that there is an issue with the website, and you need to fix it immediately. With Git, you don't have to deploy your fix along with the `iss53` changes you've made, and you don't have to put a lot of effort into reverting those changes before you can work on applying your fix to what is in production." And the demo-able fact: "when you switch branches, Git resets your working directory to look like it did the last time you committed on that branch." https://git-scm.com/book/en/v2/Git-Branching-Basic-Branching-and-Merging (text from https://github.com/progit/progit2, CC BY-NC-SA 3.0). VERIFIED.
- **GitHub Flow** — "GitHub flow is a lightweight, branch-based workflow. The GitHub flow is useful for everyone, not just developers." Steps: create a branch → make changes → create a pull request → address review comments → merge your pull request → delete your branch. The two sentences for the slide: "By creating a branch, you create a space to work without affecting the default branch." "Your changes will not end up on the default branch until you merge your branch." https://docs.github.com/en/get-started/using-github/github-flow . VERIFIED. (Simplest production-branch model; no develop/release branches.)
- **Learn Git Branching, `intro/branching`** — "Branches in Git are incredibly lightweight as well. They are simply pointers to a specific commit -- nothing more. This is why many Git enthusiasts chant the mantra: branch early, and branch often". Goal of the level: create `bugFix` and switch to it. VERIFIED.
- **Software Carpentry** — deliberately excluded from the core lesson: "Because of this complexity, we don't teach novice learners about many interesting topics, such as branching, hashes, and commit objects." (instructor notes; 13 episodes, none on branching). VERIFIED. This is the precedent for keeping branches demo-only.
- **Happy Git ch. 22 "Branches"** — "Branching means that you take a detour from the main stream of development and do work without changing the main stream. It allows one or many people to work in parallel without overwriting each other's work. It allows a someone working solo to work incrementally on an experimental idea, without jeopardizing the state of the main product." https://happygitwithr.com/git-branches . VERIFIED. (Placed in the "fundamentals" part, after the daily workflow — same ordering as this course.)
- **Julia Evans, "git branches: intuition & reality" (2023-11-23)** — the intuition is "the physical 'a branch of an apple tree' metaphor" (only the offshoot commits); the reality: "In git, a branch is the full history of every previous commit, not just the 'offshoot' commits" and "Internally in git, branches are stored as tiny text files which have a commit ID in them." https://jvns.ca/blog/2023/11/23/branches-intuition-reality/ . VERIFIED. Use: warn students the tree picture is a lie of omission; the demo should show `git log --oneline --graph --all`.

One-line analogies teachers use:
1. "A detour from the main stream" — Happy Git ch. 22 (sourced, above).
2. "A space to work without affecting the default branch" / "a safe place to make changes" — GitHub Flow (sourced, above).
3. "Parallel universe" — UNSOURCED in the references checked (common in talks; no primary text found). Safe to use as your own words.
4. "Draft copy of the website while the real one stays live" — UNSOURCED; it is the Pro Git hotfix story in plain words, so attribute the story, not the phrase.

Hammer point for the demo slot: *production never breaks because nobody edits production; the branch is where you are allowed to be wrong.* (Pairs with Session 4: an agent should work on a branch, and `git diff main` is how you read what it did.)

## 4. Candidate 2h structures

Constraints: terminal recap included; commit loop + push mandatory; VS Code Source Control panel as viewer only; 5–10 min instructor-only branch demo; SWC's own numbers say init→commit→history ≈ 60 min and GitHub remotes ≈ 45 min, so a 2h room has ~15 min of motivation budget, not 30.

### Structure A — "Undo first" (SWC/Pro Git order: SOLO → commands → COLLAB → push)
| min | block | content |
|---|---|---|
| 0–8 | Motivation I (SOLO) | PhD comic + Gentzkow & Shapiro's Stata file listing → "Who uses undo?" (SWC) → Heartbleed `git log` answer |
| 8–20 | Terminal recap | `pwd ls cd mkdir mv cp cat`; make the folder that becomes the course repo |
| 20–55 | The loop | `git init` → `status` → `add` → `commit -m` → `log`; repeat 3×; `diff` once; VS Code panel shown as the same information |
| 55–65 | Motivation II (COLLAB) | kernel: ~40 M lines, 2,652 people, ~11 commits/hour; Octoverse 180 M; Bryan: "the pros only outweigh the cons when… collaborating" |
| 65–95 | Push/pull | remote, first push (auth path from `s1-git.md`), edit on GitHub, `pull` |
| 95–105 | Branch demo (instructor) | Pro Git hotfix story live: `switch -c hotfix`, commit, `switch main`, watch the file change, merge; `log --graph --all` |
| 105–120 | Wrap + agent-era | "commit before the agent touches the repo; `git diff` is how you review it"; homework |
Hammer points: (1) "Version control is an undo command for everything" (G&S). (2) "Not one piece of software on your phone was written with the date-and-initial method" (G&S). (3) "11 commits an hour, one codebase, no email attachments." (4) "The branch is where you are allowed to be wrong." (5) "An agent without git is a liability."
Risk: the collaboration pitch lands after 55 minutes of typing, when energy is lowest; the push block is the historical sinkhole, so the branch demo is what gets cut.

### Structure B — "Collaboration first" (Bryan's order: COLLAB → SOLO → commands)
| min | block | content |
|---|---|---|
| 0–12 | Motivation (both, COLLAB first) | Torvalds 2005 mail → first commit next day → kernel numbers → Octoverse; then flip: "the same tool is the best undo you will ever have" (PhD comic, G&S) |
| 12–22 | Terminal recap | as A |
| 22–52 | The loop | as A, 30 min |
| 52–82 | Push/pull | as A, started earlier so it can overrun |
| 82–92 | Branch demo | Pro Git hotfix story + GitHub Flow six steps on one slide |
| 92–105 | Audit | `git log`, `git diff HEAD~1`, GitHub commit view: "what changed, who, when, why" (Missing Semester's four questions); preview of S4 |
| 105–120 | Buffer + wrap | catch stragglers on the push; homework |
Hammer points: (1) "One codebase, 2,652 people, 64 days, zero email attachments." (2) "Every clone is a full copy — GitLab lost its database in 2017, not one git repo." (3) "Track Changes on steroids" (Bryan). (4) "Production never breaks because nobody edits production." (5) "In Session 4 your collaborator is a robot; git is how you check its work."
Risk: opens with numbers about strangers' code, which economics students may file under "not my problem"; the flip to SOLO must be fast and explicit or the first 12 min feel like trivia.

### Structure C — "Data model first, motivation as questions" (Missing Semester order, compressed)
| min | block | content |
|---|---|---|
| 0–10 | Motivation as four questions | "Who changed this line? When? Why? What did the project look like last Tuesday?" — then the PhD comic as the failed answer; Heartbleed as the successful one |
| 10–18 | The model on a whiteboard | snapshot ≠ diff; commit = photo of the folder + message + author + parent; branch = sticky note on a photo (LGB wording) |
| 18–28 | Terminal recap | as A |
| 28–60 | The loop | commands introduced as "how to take the photo / read the album" |
| 60–70 | COLLAB numbers | kernel + Octoverse + Bryan's line, as the reason the album lives on a server |
| 70–100 | Push/pull | as A |
| 100–108 | Branch demo | sticky-note picture becomes `git log --graph`; hotfix story |
| 108–120 | Wrap + agent-era | as A |
Hammer points: (1) "An ugly interface has to be memorized; a beautiful design can be understood." (2) "A commit is a photo of the whole folder, not a list of edits." (3) "Git answers who/when/why for every line, forever." (4) "A branch is a sticky note, moving it costs nothing." (5) "Commit, then let the agent loose; diff, then decide."
Risk: 8 min of model before any typing is the longest a non-programmer room will tolerate; if the whiteboard part runs long the push block starves. Best fit if the teacher is comfortable drawing rather than reading slides.

Recommendation: A for a room that did little Session 0 practice (motivation is short and concrete, typing starts by minute 8); B if the teacher wants the collaboration message to be the memory of the day; C only with a whiteboard and a rehearsed 8-minute drawing.

## 5. Pedagogical risks and what NOT to say

- **Do not sell Git as a backup.** Toy Story 2 and GitLab 2017 are backup/ops stories; Bryan says it explicitly: "There are much easier ways to get versioned back ups of your files, if that's all you're worried about." Use them only for "a copy is not a history" and "every clone is a full copy". A student who hears "backup" will ask why not Dropbox, and the honest answer (Bryan's) is: for solo backup, Dropbox is fine.
- **Do not open with jargon.** Evans's 2023 list (HEAD, index/staged, reset/revert/restore, detached HEAD, tree-ish) is the blacklist for the first 30 minutes; SWC skips "branching, hashes, and commit objects" entirely.
- **Do not promise "two weeks".** Torvalds's own account is self-hosting in a day and "about ten days"; the code was "fairly small". Say "about ten days, after three years of using BitKeeper".
- **Do not cite github.com/about counters** (undated, 225M vs Octoverse's dated 180M); cite Octoverse with its data window.
- **Do not moralize Heartbleed.** The commit and advisory are public; the point is that git answered "who/when/what/reviewed by" two years later, not that a named person was at fault.
- **Do not let the collaboration pitch imply students must collaborate today.** The bar is a personal repo; collaboration is the Session 4 agent and the future journal replication package (AEA policy).
- **Do not teach branches with the apple-tree picture alone** (Evans): show `git log --graph --all` in the demo so "branch = pointer" is at least seen once.
- **Timing risk is structural, not motivational**: SWC budgets 45 min for the GitHub episode alone. Whatever structure is chosen, the push block needs the fixed auth path from `research/s1-git.md` §3 and a 10-minute buffer; the branch demo is the designated sacrifice, not the motivation.
