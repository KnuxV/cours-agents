# Task 02 — Build the course site (GitHub Pages) and the presenterm decks

## Role
You are a builder agent. You produce the static site and the slides. You read `research/` notes; you do not do new web research beyond checking tool docs, and you do not edit SPEC.md.

## Prerequisite
Task 01 is complete. Where a research note marks something UNVERIFIED, the site/slides must carry a visible `TODO(verify)` marker, not a confident claim.

## Goal A — Static site
MkDocs with the Material theme, deployed to GitHub Pages via a GitHub Actions workflow.

Structure (`site/` holds `mkdocs.yml` and `docs/`):
- `index.md` — course pitch (from SPEC.md thesis), schedule, links.
- `setup.md` — Session 0 verbatim-followable instructions: WSL path, Mac path, Git Bash fallback, Codespaces lifeboat, Unistra API key procedure (from the spec + s0 research note). This page is the one students will actually read under stress: every command copy-pasteable, every step numbered, screenshots optional but placeholders allowed.
- `sessions/s1.md` … `s4.md` — per session: goals, outline, links to the deck, the exercises, and the deeper-dive resources from research (top 5 only).
- `exercises.md` — index of all exercises with difficulty tags.
- `resources.md` — the configs and payloads from `resources/`, embedded with copy buttons, plus the Unistra links table.
- `replication.md` — the optional research-track module page.

Requirements:
- `mkdocs build --strict` passes (no broken internal links).
- Deploy workflow: `.github/workflows/site.yml`, builds on push to main, publishes to gh-pages. Use the standard mkdocs-material recommended action; pin versions.
- Keep styling stock Material. No custom CSS beyond a logo/color tweak. Content over chrome.

## Goal B — Slides (presenterm)
One deck per session in `slides/`: `s1-git.md`, `s2-tooling.md`, `s3-api.md`, `s4-opencode.md`. Presenterm-flavored markdown (front matter title, `<!-- end_slide -->` separators, code blocks with language tags; use presenterm's pause/incremental features sparingly).

Per-deck requirements:
- Target 2h of presentation: ~25–35 slides, most slides < 40 words. Slides are prompts for the speaker, not documents — the site holds the prose.
- Every live-demo moment in the spec becomes a slide pair: SETUP slide (the exact commands/payload, copy-pasteable) + LANDING slide (the one-sentence takeaway, e.g. "The model did not run anything. It returned a request.").
- s3 deck must include the token/cost slide, the statelessness demo, the edited-assistant-message demo, temperature 0 vs 1.5, and the tool-calling punchline, in that order.
- s4 deck must include: provider config walkthrough, the observed loop, permissions, AGENTS.md, grill/build live build, and the A/B/C empirical exercise brief.
- Speaker notes: use presenterm comments for timing marks (`<!-- 0:20 -->`) and fallback plans (what to do if the API is down: pre-recorded output files in `resources/fallback/`).
- Each deck validates: `presenterm --validate slides/<file>.md` (confirm exact flag against current presenterm docs; if the flag differs, use the current equivalent and note it in LOG.md).

## Definition of done
- Site builds strict, workflow file present, all four decks validate.
- No content contradicts SPEC.md; UNVERIFIED items visibly marked.
- Entry in `tasks/LOG.md`: page/deck inventory, list of TODO(verify) markers, anything needing human review before first deploy.
