# Task 03 — Exercises and ready-to-use resources

## Role
You are a builder agent producing student-facing exercises and the config/payload files the course depends on. Everything you produce must RUN — you test it before calling it done.

## Prerequisite
Task 01 complete (you need the verified Unistra endpoint details and OpenCode schema). Task 02 can run in parallel.

## Goal A — Resources (`resources/`)
These are the load-bearing files of the course; a typo here breaks a live session.

1. `resources/curl/` — the Session 3 payload sequence:
   - `step1-basic.json` (one raw call), `step2-context.json` (multi-turn with system prompt), `step3-edited-history.json` (the tampered assistant message demo), `step4-tools.json` (tool declaration), `step5-tool-result.json` (feeding the tool output back).
   - `run.sh` — thin wrapper: `./run.sh step1` curls the Unistra endpoint with the right headers, expects `$UNISTRA_API_KEY`. Works in bash (WSL/Mac/Git Bash).
2. `resources/opencode/` —
   - `opencode.json` — provider block for conversation.ia.unistra.fr (`@ai-sdk/openai-compatible`, baseURL from research note, model IDs and `limit` blocks verified in Task 01), permission block (strict classroom defaults: edit ask, bash whitelist), and the agent definitions: `grill`, `build`, `reviewer` exactly as specified in SPEC.md 4.4.
   - `AGENTS.md.student` — the template students drop in their repo (assertion-before-code rule, pytest-after-every-edit, ask-don't-guess).
3. `resources/fallback/` — pre-captured outputs (JSON responses, terminal transcripts) for every live demo, so a dead API doesn't kill a session. Capture these by actually running the demos.
4. `resources/install/` — `check-setup.sh`: one script that verifies a student machine (bash present, curl, git, opencode on PATH, `$UNISTRA_API_KEY` set, one live API ping) and prints PASS/FAIL per item. This is the Session 0 forum deliverable generator.

## Goal B — Exercises (`exercises/`)
Folder per session, each exercise a single markdown file: goal, starter files if any, steps, expected outcome, and a `solutions/` subfolder. Difficulty tags: [core] everyone finishes in class; [stretch] fast students; [home] homework.

Minimum set:
- `s1/` (git): 2 core (first repo + commit cycle; recover a deleted file), 1 stretch (branch + merge conflict resolved by hand).
- `s2/` (tooling): 2 core (uv project from scratch; notebook→script with argparse), 1 home (env var + secret hygiene audit of a provided bad repo), 1 stretch (polars vs pandas on a provided dataset).
- `s3/` (API): 4 core mapping to spec 3.1–3.4 (first call + read `usage`; break statelessness then fix it with history; temperature experiment with 5 repeats at two temps — students eyeball the variance; be-the-harness round trip), 1 stretch (write the 40-line Python loop automating step 4), 1 home (cost estimate: given a token price, what did today's class cost?).
- `s4/` (OpenCode): 3 core (install + provider config + first task under strict permissions; write AGENTS.md and demonstrate one behavior change; grill/build on a provided task card), 1 stretch (the A/B/C reliability comparison with a failure-count table), 1 home (add a reviewer subagent and show one caught bug).
- `replication/` — the research-track brief: paper selection criteria (public replication package, main table reproducible on a laptop), the memo template (what reproduced / what didn't / agent's role / one honest failure), grading rubric skeleton.

Exercise quality bar:
- Every command tested end-to-end against the real Unistra endpoint (or marked BLOCKED in LOG.md if the endpoint lacks a needed feature — do not fake success).
- Expected outputs shown truncated, so students know what success looks like.
- Solutions runnable as-is.

## Definition of done
- `check-setup.sh` passes on a clean environment you set up yourself.
- Every step*.json validated against the live endpoint; every exercise solution executed.
- `tasks/LOG.md` entry: test matrix (what was run where), BLOCKED items, and the three exercises most likely to overrun their time budget.
