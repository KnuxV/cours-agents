# Task 01 — Research: harden the spec and curate deeper-dive material

## Role
You are a research agent. You read, search, verify, and write notes. You do NOT edit SPEC.md, slides, or exercises.

## Goal
For each session of `SPEC.md`, produce a research note that (a) verifies every factual claim the course will make, (b) curates the best external material for students who want to go deeper, (c) flags anything in the spec that is outdated, wrong, or pedagogically risky.

## Inputs
- `SPEC.md` (the contract)
- Web search
- The Unistra docs: documentation.unistra.fr (Intelligence_artificielle section), conversation.ia.unistra.fr/api/models

## Outputs
One file per session in `research/`: `s1-git.md`, `s2-tooling.md`, `s3-api.md`, `s4-opencode.md`, plus `s0-setup.md` and `replication-module.md`.

Each file has exactly these sections:
1. **Claims check** — every checkable claim in that spec section, with status VERIFIED (source link) / UNVERIFIED / WRONG (with correction). Priority items:
   - Does the Unistra endpoint support the `tools` / `tool_calls` fields (OpenAI function calling)? This decides whether sessions 3.4 and 4 work as written. Find the exact endpoint path and test payloads if documented.
   - Exact model IDs on conversation.ia.unistra.fr and their context/output limits.
   - Current OpenCode config schema: provider block, agent definitions, permission syntax (docs at opencode.ai/docs — verify against current version, the schema moves).
   - Current WSL install behavior on Win 10/11, known failure modes and rates.
   - presenterm: install method, validate command, feature set relevant to us.
2. **Best deeper-dive resources** — max 5 per session, ranked, one line each on why it earns its place. Prefer primary docs and one excellent tutorial over listicles. Include at least one "for the ambitious student" item (e.g. Karpathy-style token/LLM internals for s3; agent-evaluation reading for s4).
3. **Pedagogical risks** — anything likely to fail live in class (rate limits, flaky tool calling, install traps) with a suggested mitigation.
4. **Suggested spec edits** — bullet list, phrased as diffs to SPEC.md, for the human to accept or reject. Do not apply them.

## Additional output: teacher preparation list
One extra file, `research/teacher-prep.md`: the minimal mastery list for the instructor before teaching sessions 3–4. Not student material — assume Python/NLP background, terminal fluency, but patchy hands-on agent experience. For each item: what to master, why it will come up in class (likely student question or live-demo failure), the single best resource, and a realistic time estimate. Keep the whole list under ~10 items, ordered by priority, total prep budget ~1 working day. Must cover at least: the OpenAI chat-completions request/response schema well enough to debug a malformed payload live; tool-calling message flow including multi-turn tool results and common failure modes of open-weight models (malformed JSON, skipped calls); OpenCode's current config schema and where it breaks; presenterm driving (navigation, live code blocks); and the top 5 questions students who use ChatGPT daily will ask (e.g. "why is this dumber than ChatGPT", "is it reading my files", "can I just use Copilot") with honest one-paragraph answers.

## Constraints
- Every resource link must be fetched and confirmed live. Dead or paywalled links are excluded.
- No more than ~1 page per section per file. Curation is the job; dumping is failure.
- For the replication module: locate Scott Cunningham's actual writing on AI-assisted replication and 2–3 published examples of LLM-assisted replication in economics. If examples are thin, say so — that shapes how the module is framed.

## Definition of done
- All six session files plus `teacher-prep.md` exist, every claim in section 1 has a status, zero invented links.
- A summary entry in `tasks/LOG.md` listing: WRONG claims found, top 3 pedagogical risks, and the single most important unresolved UNVERIFIED item.
