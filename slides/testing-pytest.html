0 — Pourquoi

Ça tourne, donc c'est juste ?

Un crash, on le voit. Le vrai danger est silencieux :

  • un filtre qui supprime les lignes avec une valeur manquante
  • une jointure qui duplique un tiers des observations
  • un tokeniseur qui met en minuscules dans une branche du code et pas dans l'autre

Rien ne plante. Le résultat est juste faux — et il part dans un rapport, un article, un mémoire.

0 — Définition

Un test, c'est quoi ?

Du code qui exécute votre code et compare ce qu'on attend à ce qu'on obtient.

# le code
def count_words(text):
    return len(text.split())

# le test
assert count_words("le chat dort") == 3

Si c'est vrai : rien. Si c'est faux : une erreur qui dit où.

1 — doctest

La docstring qui se vérifie

def count_words(text):
    """Count the words in a text (separated by whitespace).

    >>> count_words("le chat dort")
    3
    >>> count_words("  le   chat  ")
    2
    >>> count_words("")
    0
    """
    return len(text.split())

>>> : ce qu'on taperait dans Python. La ligne d'après : la réponse attendue.

1 — doctest

Pour quoi faire

Bien pour

  • montrer comment appeler la fonction
  • une documentation qui ne peut pas mentir
  • 2 ou 3 cas simples

Mal pour

  • beaucoup de cas
  • les nombres à virgule (0.30000000000000004)
  • les DataFrames, les fichiers, tout ce qui s'affiche sur plusieurs lignes

Gardez-les courts. pytest sait les lancer aussi : uv run pytest --doctest-modules.

2 — assert

assert, la brique de base

assert count_words("le chat dort") == 3
# vrai : il ne se passe rien

assert count_words("") == 0, "un texte vide a zéro mot"
# faux : AssertionError: un texte vide a zéro mot

assert + une condition + (optionnel) un message.

Tout pytest repose là-dessus. Il n'y a rien d'autre à apprendre pour écrire un test.

2 — assert

Les limites d'assert seul

  • il s'arrête au premier échec : les lignes 4 et 5 n'ont jamais tourné
  • pas de bilan : combien passent ? combien échouent ?
  • il faut penser à lancer le script
>>> 0.1 + 0.2
0.30000000000000004
>>> 0.1 + 0.2 == 0.3
False

Il nous faut un outil qui trouve les tests, les lance tous, et explique chaque échec. C'est pytest.

3 — pytest · bonnes pratiques

Un bon test

def test_normalize_strips_and_lowercases():   # 1. un nom qui dit ce qu'on vérifie
    text = "  Le Chat "                        # 2. préparer
    result = normalize(text)                   #    agir
    assert result == "le chat"                 #    vérifier
  • un nom qui parle : c'est ce qu'on lit quand ça échoue
  • une seule raison d'échouer par test
  • indépendant : ne compte jamais sur un autre test lancé avant

3 — pytest · bonnes pratiques

Les bugs vivent aux bords

  • vide : "", [], un CSV avec seulement l'en-tête
  • un seul élément
  • zéro, les négatifs — surtout au dénominateur
  • valeurs manquantes : None, NaN, une cellule vide
  • espaces en trop, majuscules, accents, "İ".lower()
  • ce qui doit être refusé

Le cas normal, c'est celui auquel vous pensiez en codant. C'est le moins susceptible d'être faux.

3 — pytest

Un test, plusieurs valeurs

import pytest

@pytest.mark.parametrize(
    "text, expected",
    [
        ("le chat dort", 3),
        ("  le   chat  ", 2),
        ("", 0),
        ("l'enfant dort", 2),        # un choix : l'apostrophe ne coupe pas
        ("Bonjour, le monde !", 4),  # un choix : "!" compte comme un mot
    ],
)
def test_count_words(text, expected):
    assert count_words(text) == expected

3 — pytest

Erreurs attendues, nombres à virgule

# une entrée invalide doit être refusée
def test_type_token_ratio_refuses_empty_list():
    with pytest.raises(ValueError):
        type_token_ratio([])


# ne jamais comparer des flottants avec == tout seul
def test_type_token_ratio_with_repetitions():
    assert type_token_ratio(["a", "b", "a"]) == pytest.approx(0.667, abs=0.001)

raises échoue si l'erreur n'arrive pas. approx tolère une petite différence.

3 — pytest · en bref

Fixtures : préparer une fois

# conftest.py
@pytest.fixture
def tokens():
    return ["le", "chat", "voit", "le", "chien"]

# tests/test_text_tools.py
def test_type_token_ratio_on_fixture(tokens):
    assert type_token_ratio(tokens) == pytest.approx(4 / 5)

def test_count_words_in_file(tmp_path):      # fournie par pytest
    corpus = tmp_path / "corpus.txt"
    corpus.write_text("le chat dort\nle chien aussi\n", encoding="utf-8")
    assert count_words_in_file(corpus) == 6

Le nom en paramètre suffit : pytest prépare la donnée, neuve pour chaque test.

3 — pytest · en bref

Mock : remplacer ce qu'on ne teste pas

label_review() demande au LLM d'Unistra si un avis est positif, puis lit sa réponse.

import labeler

def test_answer_with_capital_and_full_stop(monkeypatch):
    monkeypatch.setattr(labeler, "ask_llm", lambda prompt: "Negative.")
    assert labeler.label_review("Arrivé cassé") == "neg"

Pendant ce test, ask_llm est une fausse fonction qui répond toujours "Negative.".

On ne teste pas le LLM, on teste notre code autour. Pas de réseau, pas de clé, même réponse à chaque fois.

4 — Démo · étape 6

Corriger clean()

def clean(reviews):
    reviews = reviews.copy()
    reviews["text"] = reviews["text"].str.strip()
    reviews["lang"] = reviews["lang"].str.strip().str.lower()
    reviews = reviews[reviews["text"].notna() & (reviews["text"] != "")]
    return reviews

5 — Exercice 2 · 15 min

Tests d'abord : rouge, vert, propre

1. ROUGE   écrire UN test          → il échoue (la fonction ne sait pas encore)
2. VERT    écrire le minimum de code → il passe
3. PROPRE  améliorer le code        → les tests passent toujours
            puis le test suivant

La fonction : parse_number() lit un nombre écrit à la française.

parse_number("1 234,56")   # → 1234.56
cd ~/testing-lab/exo2-tdd
uv run pytest          # rouge : NotImplementedError

5 — Exercice 2

Un test à la fois

ÉtapeTest à écrire
1"12" → 12.0 (déjà écrit)
2"12,5" → 12.5
3"1 234,56" → 1234.56 · bonus : l'espace insécable "1 234,56"
4"-3,2" → -3.2 · " 7 " → 7.0
5"", "abc" → ValueError (avec pytest.raises)
6"1.234,56" ? "1,234.56" ? — à vous de décider

Après chaque test : lancer, voir rouge, coder, voir vert. Puis seulement le suivant.

5 — Exercice 2 · discussion

Quand est-ce assez bien ?

  • "1.234,56" s'écrit ainsi en allemand, "1,234.56" en anglais. Accepter ? Refuser ? Deviner ?
  • "12,5 %" ? "1 234,56 €" ?
  • assez bien = les cas que vos données contiennent vraiment, plus ceux qui doivent être refusés

Vos tests sont votre cahier des charges : chaque décision y est écrite, et vérifiée à chaque lancement.
