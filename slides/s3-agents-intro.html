Meta-programming · Session 3

What is inside the chatbot

Three parts: this, then driving a real agent in your terminal, then exercises where it is wrong and you catch it. One of the slides you type yourself.

By the end, five words you can define without hand-waving — model · API · context · tool · skill — and then, for free, agent.

Where you are now

A chatbot

You ask. It answers. Nothing in the world changes.

You copy the code, you paste it, you run it. You are the machinery.

An agent

You ask. It reads your files, runs commands, writes files, reads the errors, tries again.

Something changes — on your disk, under your account.

Same model in both columns. The difference is engineering, not intelligence.

1 — The model

A frozen function

  • trained once, at enormous cost, then frozen
  • it predicts the next piece of text, over and over
  • between two calls it learns nothing and remembers nothing

The weights are the coefficients. Nobody re-estimates them because you talked to it.

The unit of account

Tokens

"econometrics"  →  "econom" + "etrics"     2 tokens
"survey.csv"    →  "survey" + "." + "csv"  3 tokens

Everything is counted in them: what you send, what comes back, the price you pay, and the limit on how much the model can see at once.

Tokens are the price system of this entire industry.

2 — The API

A counter with a fixed contract

The model runs on a machine you will never touch. Between you and it there is one address, and one agreed shape for the paperwork.

POST https://conversation.ia.unistra.fr/api/chat/completions
Authorization: Bearer $UNISTRA_API_KEY
Content-Type: application/json

An API is the paperwork, not the intelligence. Every chatbot, every agent, every plugin you have ever used is this request with a different wrapper.

The request, field by field

// question.json
{
  "model":    "coder",          ← which model answers. A choice with a price.
  "messages": [ ... ],          ← everything it will know. See next slide.
  "temperature": 0              ← 0 = the most likely words, every time.
}

Three fields. There is no fourth thing where the intelligence hides.

Three roles, and that is all

"messages": [
  {"role": "system",    "content": "You are a teaching assistant.
                              Answer in one short sentence."},
  {"role": "user",      "content": "What is a token?"},
  {"role": "assistant", "content": "A token is a piece of a word..."}
]
systemstanding instructions — the job description, set once, in front of everything
useryou
assistantwhat the model said last time — stored and re-sent by you

There is no fourth place where a conversation lives.

Send it yourself

curl -s https://conversation.ia.unistra.fr/api/chat/completions \
  -H "Authorization: Bearer $UNISTRA_API_KEY" \
  -H "Content-Type: application/json" \
  -d @question.json | python3 -m json.tool

One question. One answer. No agent, no tools, no loop — the whole of what a chatbot does, in one line of terminal.

Your key never appears in the file. $UNISTRA_API_KEY is read from your environment at the moment of the call.

What comes back

{
  "choices": [{"message": {"role": "assistant",
                          "content": "A token is a piece of a word..."}}],
  "usage": {"prompt_tokens": 38, "completion_tokens": 14,
            "total_tokens": 52}
}
  • the answer is one field of a JSON document — the rest is packaging
  • no session id, no memory, nothing tying this reply to your next request

Input tokens, output tokens

what it countsbehaviour
prompt_tokens
input		everything you sent: system prompt + whole history + pasted files + tool definitionsgrows every turn, and is paid again every turn
completion_tokens
output		only what the model wrote this timeusually smaller — and priced several times higher per token

A long conversation is not expensive because of what it says. It is expensive because you keep re-sending it.

3 — Context

“Make it faster.”

{"model": "coder", "messages": [{"role": "user",
                                 "content": "Make it faster."}]}

Make what faster? The model never saw the first message. Each call starts from zero.

A conversation is a re-send

{"messages": [
  {"role": "system",    "content": "You are a helpful assistant."},
  {"role": "user",      "content": "Write a function that sorts a list."},
  {"role": "assistant", "content": "def my_sort(...): ..."},
  {"role": "user",      "content": "Make it faster."}
]}

Every turn, the whole transcript goes back up. So “memory” is a file you re-upload — and a file can be edited.

Context is constructed, not recalled.

The context window

Everything must fit: standing instructions + the whole transcript + the files you pasted + the tool definitions + the tool outputs.

modelwindow
ministral — 3B, Unistra32 768~25 000 words
coder — 80B, Unistra262 144~200 000 words · two novels
GPT-5.5 · Claude Opus 51 000 000~750 000 words · a shelf

Roughly ¾ of an English word per token. The frontier models are about four times the local coder — and you pay for every token of it, every turn.

And before the hard limit, a soft one: a model gets worse as its context fills, long before it is full. A three-hour session is not just dearer — it is dumber.

Watch it: /session inside pi prints the token count of the conversation. When it climbs, /compact summarises it, and /new starts clean. Fresh context plus a short written brief beats a long transcript, every time.

4 — Tools

You add a paragraph. Not code — a description.

"tools": [{"type": "function", "function": {
  "name": "run_bash",
  "description": "Run a shell command and return its output",
  "parameters": {"type": "object",
                 "properties": {"command": {"type": "string"}}}}}]

You are telling the model: these are the actions you may ask for.

The punchline

{"choices": [{"finish_reason": "tool_calls",
  "message": {"content": null,
    "tool_calls": [{"function": {"name": "run_bash",
      "arguments": "{\"command\": \"ls *.md | wc -l\"}"}}]}}]}

"content": null — there is no answer. The model did not run anything. It returned a request.

Someone must execute it and send the result back. That someone is a program. That program is the harness.

What else can it ask for?

pi hands the model seven tools out of the box:

read   bash   edit   write   grep   find   ls

You can add your own: an MCP server (a database, your university's API, a calendar), a Python function you wrote, a web search, a plotting tool.

But every tool's name and description sits in the context of every request. Twenty tools cost tokens and make the choice harder — and bash already covers most of what people rush to add.

5 — The loop

An agent

        you: "find the income gap by region"
                      │
                      ▼
 ┌───▶   model   ───▶  asks for a tool?  ──no──▶  answers you
 │         ▲               │
 │         │              yes
 │         │               ▼
 │         │        the harness runs it
 │         │               │
 └─────────┴───────────────┘
      result appended to the context

The loop ends when the model stops asking — that is, when it decides it is done.

“Done” is its own judgement, not a check. Which is why everything reliable sits outside the loop: a test that fails, git, a second agent that only reads.

Three things people call “AI”

who decides the stepswhat it looks like
chatbotyou, one turn at a timeyou paste a traceback into a tab and it explains it
workflowthe programmer, in advancea script that walks 800 open-ended survey answers and asks the model to classify each one
agentthe model, at run time“find out why my regression drops 200 rows, and fix it” — in your terminal, in twenty minutes

Only the third one is a delegation. You set the objective; it chooses the means.

A workflow worth writing

# classify.py — you decide every step
for answer in open_answers:              # 800 survey responses
    label = ask_model(PROMPT + answer)   # one call, one job
    rows.append((answer, label))
write_csv(rows)
  • the same prompt every time — so you can test it on twenty rows first
  • one job per call — nothing accumulates, nothing drifts
  • it crashed at row 512? restart at row 512

Most of what people want an agent for is a workflow. If you can write the steps down, write them down.

6 — Skills

A folder with a text file in it

data-check/
  SKILL.md        ← name, a description, the procedure
  references/     ← optional, read only when needed
  • the harness shows the model only the name and one-line description
  • the model asks for the full text when a task matches
  • a hundred skills cost almost nothing until one is used

The onboarding binder for a colleague who starts from zero every morning.

A skill, in full

.agents/skills/tests-first/SKILL.md
---
name: tests-first
description: Writing a test before writing or changing code, and
  running it. Use when asked to add a function, fix a bug, refactor.
---
# Tests first

A change is not finished because it looks right. It is finished
when something that failed now passes.

1. Write the assertion first. Show it failing — paste the real output.
2. Write the least code that makes it pass.
3. Run the whole suite. A test you have not run is a claim.
  1. at startup, pi reads the name and description of every skill and puts that one-line list in the system prompt;
  2. when the model judges a task matches, it reads the file;
  3. the text is dropped into the conversation — like a message nobody typed.

A skill is text arriving at the right moment. No training, no magic — which is why writing it well is entirely your job.

Your four dials

dialthe questionhow you turn it
modelwho does the work?/model — inside pi, any time
contextwhat does it know?AGENTS.md in the folder · @file · /new
toolswhat may it do?pi --tools read,grep,find,ls — when you launch it
skillswhich procedure?.agents/skills/<name>/SKILL.md · /skill:<name>

Three of them you turn mid-session. The tool list you choose before you start — which is exactly why it is the one hard guarantee.

Limitations

  • hallucination is not rare — it is the normal behaviour of a system optimised to always produce a plausible continuation
  • sycophancy — it agrees with you. Say “that coefficient looks wrong” and it will find a reason. Push twice and it will abandon a correct answer
  • it never says “I do not know” unless you make room for it to
  • it is not reproducible — same prompt, same data, different code tomorrow
  • a discrepancy is a finding, not a bug — an agent asked to “fix” one will smooth it away

So what is it actually good for

Good

  • boilerplate, glue, plotting
  • translating code between languages
  • reading an unfamiliar codebase
  • the tedious 80% of data cleaning
  • explaining an error message
  • writing the tests you avoid writing

Bad

  • deciding what the question is
  • identification, causality, judgement
  • anything you cannot check
  • long unmonitored autonomy
  • being trusted about its own work

The job that disappears is typing. The job that grows is specifying and verifying.

3 · a second skill

A small dashboard

/skill:figure-style
Three figures from survey.csv: income by education, income by region,
and experience against income. Save them under out/, then write
out/report.md with one sentence under each figure.

Labelled axes with units, the n stated, bars sorted by value — because a file said so, not because you asked nicely.

4 · a fresh context

Tests, written by someone else

# a SECOND terminal, same folder, brand new conversation
cd ~/agent-lab && pi --tools read,bash,write

/skill:tests-first Write a pytest suite for make_survey.py.
Do not modify make_survey.py.

It cannot edit — so it cannot make a failing test pass by quietly changing the program.

A fresh context is the cheapest cure for sycophancy there is. It costs one terminal.

5 · separation of powers

The referee

# a THIRD terminal — it may read, and nothing else
cd ~/agent-lab && pi --tools read,grep,find,ls

/skill:referee Review out/report.md against survey.csv and the scripts.

Its instructions: for every number in the report, find the line of code that produced it. A number with no line behind it is a FAIL.

Three processes, one model, opposing incentives. Reliability comes from the structure, not from a bigger model.

6 · the tool nobody thinks about

Search, as a tool

Which script writes to out/, and where does the 0.11 figure
in report.md come from? Do not change anything.

Watch it: grep, then find, then read on two files. It did not load your project — it searched it, and read the three places that mattered.

A repository of four hundred files fits in no context window. A search result does. That is why search is the tool that makes the rest possible.

What you just did

The agent is a confident junior colleague with no memory of yesterday. You keep git, the tests, and the last word.

Exercise 1 · on your own

The password generator

Write a small Python program that generates passwords automatically — the kind the user asks for.

  • memorable — words joined together, cheval-ancre-banane-07: long, typeable, easy to remember
  • random — characters drawn from a set, k7$Rm2!qXz: short and hostile

The user chooses on the command line, with argparse: which kind, how long, how many, digits or not. The agent may explain; you type every line. Ask the same question twice — once to the agent, once to the official argparse documentation.

Done when --help explains your options to a stranger, and --style memorable --count 5 prints five of them.
