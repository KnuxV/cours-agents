    Session 2 — Python tooling¶

    Friday 18 September 2026, 15:00–17:00, room A330 (Idem-Lab).

    Slides: to be published (slides/s2-tooling.md). This page is the complete version.

    Goals¶

    By the end of the two hours you can:

    1. explain what pip, a virtual environment and a requirements.txt are — the classic toolkit you will meet in every existing project — and what they leave out;
    2. create a Python project with uv — pinned interpreter, declared dependencies, lockfile — and explain what each of the three files is for;
    3. turn a notebook cell with hard-coded values into a script with command-line arguments (argparse), run it with uv run, and get --help for free;
    4. install someone else's project in one command (uv sync), fork it, and extend its command line on a branch;
    5. explain what an environment variable is, store a secret for good — in ~/.bashrc or in a .env file — read it from Python, and say why it never goes in code;
    6. (bonus) read a CSV with Polars and do a group-by in five lines.

    Deliverable: a reproducible script committed to your course repository — pyproject.toml, uv.lock, .python-version, report.py — and UNISTRA_API_KEY surviving a new terminal. The second item is Session 3's prerequisite; without it, Session 3 begins with a 401.

    Before class¶

    • Your course repository from Session 1 exists on GitHub and on your machine.
    • Your Unistra API key is stored as an environment variable (setup, section 5). Test in a new terminal: echo $UNISTRA_API_KEY | cut -c1-6 prints sk-XXX.
    • Ten minutes of reading: uv — Working on projects, sections Creating a new project to Managing dependencies.
    • Five minutes: the README of github.com/KnuxV/password-generator, the project you will fork in class.
    • You do not need to install Python. uv installs the exact version the project asks for, by itself. (Section 2 uses whatever python3 your machine already has, if any; python3 --version tells you.)

    1. Why: "it works on my machine" is not a result¶

    Your workflow so far is Colab: open a browser, get a machine with some Python and some packages, run cells until the table appears. Which Python? Which pandas? Whatever Google installed that month. Re-run the notebook next year and the numbers may differ, or the code may not run at all — and you will not know which of the two hundred libraries changed.

    For a scientist that is not an inconvenience, it is a validity problem. A result nobody can reproduce, including you in six months, is a claim, not a finding. Journals and data editors now require the replication package to pin its environment (the optional replication track is built on exactly this). Three things must be fixed for a Python project to be reproducible:

    Layer Question Answered by
    The interpreter Which Python? 3.12, not "whatever python is" .python-version
    The direct dependencies Which libraries did I ask for? pyproject.toml
    The exact resolved set Which exact versions of those, and of everything they pull in? uv.lock

    Python's classic answer to these questions is a trio of tools — pip, venv, requirements.txt — that you will meet in every project written before 2024 and in most tutorials, so section 2 shows them first. From section 3 on we use uv, one tool that does the same job, completely, faster, on every platform.

    2. The classic toolkit: pip, venv, requirements.txt¶

    Read this section on any machine; type it if python3 --version prints a version (WSL, Mac, Codespaces). Git Bash users: read along — there is no Python on your machine yet, and that is one of the things uv fixes in section 3.

    2.1 pip install and the one-Python problem¶

    Python ships with a package installer, pip. pip install polars downloads polars from PyPI (the Python Package Index, the public catalogue every import you have ever typed came from) and copies it into the Python that ran pip. Colab does exactly this when a cell says !pip install something.

    On your own machine the trouble starts with the word the. There is one Python, and every project installs into it. Your thesis needs pandas 1.5; a tutorial you follow next week installs pandas 2.3 on top; the thesis code now breaks, and six months later you cannot say which of the two hundred packages in that Python your thesis actually used. The system Python on Ubuntu and macOS is also used by the operating system itself, which is why pip install there is refused outright on recent versions (externally-managed-environment).

    2.2 A virtual environment: one Python per project¶

    The fix, since 2012, is the virtual environment: a folder inside the project that holds a private Python and its own packages. Make one by hand, once, to see what it is:

    Ubuntu window, Terminal (Mac), or Codespace terminal
    mkdir ~/venv-demo
cd ~/venv-demo
python3 -m venv .venv
ls -a
ls .venv/bin

    python3 -m venv .venv creates the folder .venv (the name is a convention). Inside, bin/ holds a python, a pip, and a script called activate. Nothing is installed yet. (On WSL, if this complains about ensurepip, Ubuntu ships Python without that piece: sudo apt install python3-venv, then retry.)

    Now activate it:

    Same terminal, inside venv-demo
    source .venv/bin/activate
which python
pip install polars
python -c "import polars; print(polars.__version__)"

    Three things to notice. Your prompt now starts with (.venv). which python answers /home/you/venv-demo/.venv/bin/python — the private one, not /usr/bin/python3. And pip install polars therefore went into .venv, nowhere else. Activation is nothing magical: activate puts .venv/bin at the front of your PATH for this window, so that python and pip resolve to the private copies.

    Prove the isolation, then leave:

    Same terminal
    deactivate
which python
python3 -c "import polars"

    After deactivate the prompt is back to normal, which python is the system Python again (or nothing), and the import fails with ModuleNotFoundError: No module named 'polars': polars exists only inside venv-demo/.venv. That is the whole idea — one environment per project, and the project's folder is the unit of reproducibility.

    For recognition only: on Windows (outside WSL) the scripts live in .venv\Scripts\ instead of .venv/bin/, so tutorials say .venv\Scripts\activate. Same thing.

    2.3 requirements.txt: the list you ship¶

    An environment is not shareable — it is a folder full of compiled files for your machine — but the list of what is in it is. The convention is a text file, requirements.txt, one package per line, produced by pip freeze:

    Same terminal, inside venv-demo
    source .venv/bin/activate
pip freeze > requirements.txt
cat requirements.txt
deactivate

    polars==1.44.1
polars-runtime-32==1.44.1

    Whoever receives the project runs the three-line ritual you will find in thousands of READMEs — create, activate, install from the list:

    The recipient's side (do not run it now)
    python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

    You have now seen every piece of the classic toolkit: pip installs, venv isolates, requirements.txt transmits.

    2.4 What is still missing¶

    Look at the two lines of requirements.txt against the three-layer table of section 1:

    • Which Python? Not in the file. The recipient's python3 may be 3.9 or 3.14; polars 1.44 may not even install on one of them.
    • What did I ask for? You asked for polars; polars-runtime-32 came along with it. pip freeze flattens direct and indirect dependencies into one list, so a year later nobody knows which lines can be removed.
    • Is it really the same file? Version numbers, no checksums. Rare, but a package can be re-uploaded under the same version.
    • Three commands and a trap. "Did you activate?" is the most common support question in any Python course: (.venv) is missing from the prompt, python is the system one, and the error is No module named polars although you installed it — into the other Python.

    uv keeps the good idea (the .venv folder — the same folder, with the same layout) and fixes the four gaps: the Python version is pinned in a file, your direct dependencies are declared in pyproject.toml, the exact resolved set with hashes is written to uv.lock, and activation is done for you on every command. The rest of the session is that. Clean up first:

    Any terminal
    cd ~
rm -rf ~/venv-demo
    Classic uv (sections 3–4)
    python3 -m venv .venv uv venv — or nothing: uv run creates it when needed
    source .venv/bin/activate then python x.py uv run x.py
    pip install polars uv add polars
    pip freeze > requirements.txt uv.lock, written automatically
    pip install -r requirements.txt uv sync

    The installer puts uv in ~/.local/bin and adds that folder to your PATH — for future terminals. So, the ritual you learned in Session 0: close the terminal, open a new one, then:

    Any terminal — new window

    4. A project from scratch¶

    4.1 uv init¶

    Go into your course repository and initialise a project in place (no folder name after init; the project takes the folder's name):

    Any terminal
    cd ~/agent-lab
uv init --no-package --python 3.12
ls -a

    Two flags, both deliberate:

    • --python 3.12 pins the interpreter. Without it, uv picks the newest Python it can find — different on every laptop, and your lockfiles would disagree with your neighbour's and with Codespaces.
    • --no-package gives the simple layout: one main.py at the top. (Since uv 0.12 the default is a src/ package layout with a build system — right for libraries, noise for us.)

    Expected files (plus your .git, README.md and .gitignore from Session 1):

    .python-version   pyproject.toml   main.py
    • .python-version contains 3.12. Every uv command in this folder uses that Python — downloading it first if needed.
    • pyproject.toml is the project's declaration: name, the Python requirement, and an empty dependencies = [] list. This is the standard file every Python tool reads.
    • main.py is a hello-world.

    uv init inside an existing git repository

    uv notices the .git you created in Session 1 and does not create a second one. It also does not write a .gitignore in that case — which is why Session 1 made you write one with .venv/ in it.

    4.2 uv run — the environment appears¶

    Any terminal, inside agent-lab
    uv run main.py
ls -a

    The first run prints a few lines — Using CPython 3.12.x, Creating virtual environment at: .venv — then Hello from agent-lab!. A new folder .venv exists. That is the virtual environment of section 2.2 — the very same kind of folder: ls .venv/bin shows the same activate, python and pip, and packages will land in the same place. Two differences. It holds a private Python 3.12, the version pinned in .python-version, whatever python3 your machine has (or has not). And you never activate it by hand: uv run <something> means "run this with the project's .venv", so the "did you activate?" trap of section 2.4 disappears. (If a tutorial insists, source .venv/bin/activate works on a uv-made environment too; deactivate leaves it.)

    .venv is machine-specific and large. It is never committed — it is in your .gitignore, and uv also drops a .gitignore inside it as a belt-and-braces. Anyone who clones your repo recreates it in seconds from the lockfile (section 4.4).

    4.3 uv add — declare a dependency¶

    Any terminal, inside agent-lab
    uv add polars
cat pyproject.toml
ls -a

    Three things happened:

    1. pyproject.toml now says dependencies = ["polars>=1.44.1"] — what you asked for, with a lower bound.
    2. A new file, uv.lock, lists the exact version of polars and of everything polars depends on, with a cryptographic hash of each downloaded file. Open it (head -20 uv.lock); you will never edit it by hand, but you will always commit it.
    3. Polars was installed into .venv.

    Check it works:

    Any terminal, inside agent-lab
    uv run python -c "import polars; print(polars.__version__)"

    Expected: 1.44.1 (or later, if you add it after this page was written). To remove a dependency: uv remove polars. To see the tree: uv tree.

    pyproject.toml is the wish, uv.lock is the receipt

    The first says "I need polars, at least 1.44". The second says "on 18 September 2026 that resolved to polars 1.44.1, polars-runtime-32 1.44.1, these exact files". Both are committed; the receipt is what makes the result reproducible next year.

    4.4 uv sync — reproduce it elsewhere¶

    This is the other half of the story. On any other machine (a classmate's laptop, a Codespace, the university cluster):

    Any terminal
    git clone https://github.com/YOUR-USERNAME/agent-lab.git
cd agent-lab
uv sync

    uv sync reads .python-version and uv.lock, fetches that exact Python if missing, and rebuilds .venv identically. Same numbers, guaranteed by hashes. (uv run does this implicitly too; uv sync is the explicit form you put in a README.) This is the one-line replacement for the three-line ritual of section 2.3, and it is how you will install the password generator in exercise 2.3.

    A project that only has a requirements.txt

    Older projects have no pyproject.toml or uv.lock, only the frozen list. uv reads it: inside the cloned folder, uv init --no-package --python 3.12 then uv add -r requirements.txt turns every line into a declared dependency and writes the lockfile; from then on, uv run and uv sync as usual. (There is also uv pip install -r requirements.txt, a drop-in for pip that installs into .venv without declaring anything — fine for a one-off, not for a project you keep.)

    4.5 Commit the project files¶

    Any terminal, inside agent-lab
    git status
git add pyproject.toml uv.lock .python-version main.py
git commit -m "Initialise uv project with polars"
git push

    git status must not list .venv — if it does, your .gitignore is missing the .venv/ line; add it before committing.

    5. From a notebook cell to a script with arguments¶

    5.1 The gap this session closes¶

    In a notebook, a parameter is a variable you edit at the top of the cell and re-run:

    What it looks like in Colab
    import polars as pl

CSV_FILE = "sales.csv"      # edit here…
TOP = 3                     # …and here, then Shift+Enter

df = pl.read_csv(CSV_FILE)
result = (
    df.with_columns((pl.col("units") * pl.col("unit_price")).alias("revenue"))
    .group_by("region")
    .agg(pl.col("revenue").sum())
    .sort("revenue", descending=True)
    .head(TOP)
)
result

    That works for one person, once. It cannot be run on ten files in a loop, scheduled every night, called by a colleague who does not open notebooks, or — in Session 4 — called by an agent that needs to test your code. The industry form of the same thing is a script with arguments: uv run report.py sales.csv --top 3. The values that used to be "edit the cell" are now typed on the command line.

    Get the toy data (nine rows, invented; columns region, product, units, unit_price):

    Any terminal, inside agent-lab
    curl -LO https://knuxv.github.io/cours-agents/files/sales.csv
head -3 sales.csv

    5.2 The script¶

    Create report.py with the following content (nano report.py, paste, Ctrl+O, Enter, Ctrl+X — or VS Code). Also downloadable: report.py.

    report.py
    """Total revenue per region from a sales CSV. Usage: uv run report.py sales.csv --top 2"""
import argparse
import polars as pl


def main() -> None:
    parser = argparse.ArgumentParser(description="Revenue per region from a sales CSV.")
    parser.add_argument("csv_file", help="path to the CSV (columns: region, product, units, unit_price)")
    parser.add_argument("--top", type=int, default=3, help="how many regions to show (default: 3)")
    parser.add_argument("--product", help="keep only this product (default: all)")
    args = parser.parse_args()

    df = pl.read_csv(args.csv_file)
    if args.product:
        df = df.filter(pl.col("product") == args.product)
    result = (
        df.with_columns((pl.col("units") * pl.col("unit_price")).alias("revenue"))
        .group_by("region")
        .agg(pl.col("revenue").sum())
        .sort("revenue", descending=True)
        .head(args.top)
    )
    print(result)


if __name__ == "__main__":
    main()

    Read it top to bottom; four ideas carry the whole of argparse:

    • A parser describes what the command accepts. The description shows up in --help.
    • A positional argument (csv_file) is required and identified by its position: report.py sales.csv.
    • An option (--top, --product) starts with --, is optional, and can have a default and a type. type=int converts the text "2" to the number 2 and rejects "two" with a clean error.
    • parse_args() returns an object; args.top is your old TOP variable. The rest of the function is the notebook cell, unchanged, with the two constants replaced.

    The if __name__ == "__main__": line means "run main() only when this file is executed as a script, not when it is imported". You will see it in every Python script from now on; type it, do not question it yet.

    5.3 Run it¶

    Any terminal, inside agent-lab
    uv run report.py sales.csv --top 2

    Expected:

    shape: (2, 2)
┌──────────┬─────────┐
│ region   ┆ revenue │
│ ---      ┆ ---     │
│ str      ┆ f64     │
╞══════════╪═════════╡
│ Bretagne ┆ 937.5   │
│ Alsace   ┆ 828.5   │
└──────────┴─────────┘

    Now the things you got for free:

    Any terminal, inside agent-lab
    uv run report.py --help
uv run report.py sales.csv --product tea
uv run report.py
uv run report.py sales.csv --top two
    • --help prints a usage message built from your help= strings — documentation that cannot drift from the code.
    • The third command fails with error: the following arguments are required: csv_file, the fourth with argument --top: invalid int value: 'two', both with exit code 2 and no Python traceback. Input validation, without writing any.

    Commit:

    Any terminal, inside agent-lab
    git add report.py sales.csv
git commit -m "Add revenue report script with argparse"
git push

    6. Environment variables — where secrets live¶

    6.1 What they are¶

    Every program you start receives a small dictionary of named values from the shell that started it: the environment. Some are set by the system (HOME, your home folder; PATH, the folders searched for commands); any you like can be added. Look at yours:

    Any terminal
    echo $HOME
echo $PATH
env | head -5

    $NAME reads a variable in the shell. Set one for this window only:

    Any terminal
    export GREETING="bonjour"
echo $GREETING

    Open a second terminal window and run echo $GREETING there: empty. export affects the current shell and the programs it launches, nothing else. To make a variable exist in every future window, the line goes in the shell's startup file — ~/.bashrc on WSL, Codespaces and Git Bash, ~/.zshrc on a Mac — which is exactly what setup section 5.2 had you do for UNISTRA_API_KEY. Confirm it took, in a new window:

    Any terminal — new window
    echo $UNISTRA_API_KEY | cut -c1-6

    If that prints an empty line, fix it now (wrong file, or the terminal was not reopened); Session 3 depends on it.

    6.2 Reading them from Python¶

    whoami.py
    import os

key = os.environ.get("UNISTRA_API_KEY")
if key is None:
    raise SystemExit("UNISTRA_API_KEY is not set. See the setup page, section 5.")
print("key found, starts with", key[:6])
    Any terminal, inside agent-lab
    uv run whoami.py

    Expected: key found, starts with sk-XXX. os.environ is the environment as a dictionary; .get() returns None instead of crashing when the name is absent, so the script can fail with a sentence rather than a KeyError traceback. Failing loudly and early on a missing secret is the correct behaviour — an agent reading that message knows what to do; one reading a traceback guesses.

    6.3 Two homes for a secret: ~/.bashrc or .env¶

    The key has to live somewhere on disk, or you would type it at every run. Two places are legitimate; you have used the first, and many projects you clone will expect the second.

    Home A — the shell's startup file. What setup section 5.2 did: one export UNISTRA_API_KEY="sk-XXXX" line in ~/.bashrc (or ~/.zshrc). Scope: you, on this machine, in every terminal and every project. Nothing to add to any repository. Right for a personal key you use everywhere — and it is what curl will read in Session 3, so keep it.

    Home B — a .env file in the project folder. A plain text file named exactly .env, one NAME=value per line, no export, no spaces around =:

    .env — inside agent-lab (create it with nano or VS Code)
    UNISTRA_API_KEY=sk-XXXX

    Scope: this project, for whoever runs it — a classmate, a Codespace, a CI job, a Docker container, an agent. The project declares which variables it needs; each copy of the project supplies its own values. Python does not read .env by itself; the python-dotenv package does, and it is a dependency like any other:

    Any terminal, inside agent-lab
    uv add python-dotenv
    whoami.py — the .env-aware version
    import os
from dotenv import load_dotenv

load_dotenv()  # reads .env in the current folder, if there is one

key = os.environ.get("UNISTRA_API_KEY")
if key is None:
    raise SystemExit("UNISTRA_API_KEY is not set. See the setup page, section 5.")
print("key found, starts with", key[:6])

    load_dotenv() copies each line of .env into os.environ, and the rest of the script is unchanged: it still reads the environment, it does not know or care where the value came from. A variable that already exists in the shell wins over the file (load_dotenv does not override), so Home A and Home B coexist without surprise.

    Now the part that matters. .env is never committed. Your .gitignore from Session 1 already has the line; check that Git really ignores the file, then look at git status:

    Any terminal, inside agent-lab
    git check-ignore -v .env
git status

    Expected: .gitignore:2:.env .env — the rule, its line number, the file — and a git status in which .env does not appear (whoami.py, pyproject.toml and uv.lock do; commit those). If .env shows up as untracked, add the line: echo ".env" >> .gitignore. The convention for telling others which variables to fill in is a second file, .env.example, with the names and placeholder values, which is committed:

    .env.example — committed
    UNISTRA_API_KEY=sk-XXXX

    Which home for the course? Keep A — Session 3's curl commands need the shell variable. Add B the day you share or deploy a project, and you will recognise it in every repository that ships a .env.example.

    6.4 Why the key never goes in the code¶

    Three reasons, in increasing order of seriousness.

    1. Configuration is not code. The same script runs with your key on your laptop, with a colleague's on theirs, with a test key in CI. Hard-coding it means editing the code to change who runs it. (The Twelve-Factor App — Config, two paragraphs, is the canonical statement.)
    2. Git remembers forever. You learned in Session 1 that a commit is permanent. A key pasted in report.py, committed, then deleted in the next commit is still in the history, and git log -p shows it to anyone with the repository. Bots scan public GitHub for sk- strings within minutes of a push.
    3. Agents copy what they see. In Session 4 an agent will read your files to work on them. A key in the code ends up in its context, its logs, and possibly its next commit.

    So: the secret lives in the environment — put there by ~/.bashrc or by a .env file that Git ignores; the code reads os.environ; the repository contains the name of the variable (in the README, or in .env.example), never its value. A .env file committed "just this once" is exactly reason 2: it is in the history for good.

    If a key was ever committed

    Deleting it from the file does nothing. Regenerate the key (setup 5.1) so the leaked one is worthless, then fix the repository. Come and see us; rewriting history is possible but is not a beginner operation.

    7. Bonus: Polars in five minutes¶

    You already used it in report.py. Polars is a DataFrame library like pandas, written in Rust: much faster, stricter about types, and built around expressions — pl.col("units") * pl.col("unit_price") describes a computation, and Polars runs it in an optimised plan — instead of pandas' chained indexing. Coming from pandas, the three habits to relearn:

    pandas Polars
    df[df["product"] == "tea"] df.filter(pl.col("product") == "tea")
    df["revenue"] = df["units"] * df["unit_price"] df.with_columns((pl.col("units") * pl.col("unit_price")).alias("revenue"))
    df.groupby("region")["revenue"].sum() df.group_by("region").agg(pl.col("revenue").sum())

    Try it live:

    Any terminal, inside agent-lab
    uv run python -c "import polars as pl; df = pl.read_csv('sales.csv'); print(df.describe())"

    Read next: Polars — Coming from pandas. The stretch exercise times the two libraries on a larger file.

    9. When things go wrong¶

    Symptom Cause Fix
    uv: command not found right after installing PATH is read when a terminal starts Open a new terminal. Still nothing on WSL/Mac: source ~/.bashrc (or ~/.zshrc)
    uv init says a pyproject.toml already exists You ran it twice Nothing to do
    python3 -m venv fails with ensurepip is not available (WSL) Ubuntu ships Python without venv sudo apt install python3-venv, retry
    pip install refused: externally-managed-environment You are installing into the system Python Activate a virtual environment first — or use uv add
    (.venv) not in the prompt, No module named X although you installed it Environment not activated; python is the system one source .venv/bin/activate — or uv run, which never has this problem
    Your uv.lock differs from a classmate's for the same pyproject.toml Different Python pinned Both check cat .python-version; it must say 3.12
    No module named polars You ran python report.py instead of uv run report.py Always uv run
    git status shows hundreds of files under .venv .gitignore missing .venv/ echo ".venv/" >> .gitignore, then git status again
    echo $UNISTRA_API_KEY is empty in a new window Line went in the wrong startup file, or the window is not new echo $SHELL; bash → ~/.bashrc, zsh → ~/.zshrc; redo setup 5.2
    .env exists but Python says the variable is not set load_dotenv() not called, or .env is in another folder (it reads the current directory) ls -a in the folder you run from; the file is named exactly .env
    git status lists .env .gitignore is missing the line echo ".env" >> .gitignore. If it was already committed: see the red box in section 6.4
    Failed to hardlink files; falling back to full copy warning Cache and project on different drives (e.g. work kept under /mnt/c in WSL) Harmless. Better: keep projects in ~ — see where to keep your work
    Arguments with spaces or * behave oddly Shell quoting Quote them: --product "green tea"

    10. Cheat sheet¶

    Command What it does
    uv init --no-package --python 3.12 New project in the current folder, flat layout, Python pinned
    uv add <pkg> / uv remove <pkg> Declare / undeclare a dependency (updates pyproject.toml and uv.lock)
    uv run <script.py> [args] Run inside the project's environment (creates it if needed)
    uv sync Rebuild .venv exactly from uv.lock
    uv tree Show installed packages and their dependencies
    uv python install 3.12 Fetch a Python version (usually implicit)
    export NAME="value" Set a variable for this window
    echo 'export NAME="value"' >> ~/.bashrc …for every future window (~/.zshrc on Mac)
    echo $NAME / env Read one / all variables
    os.environ.get("NAME") Read it from Python (None if unset)
    load_dotenv() (package python-dotenv) Also read a .env file in the current folder into the environment
    python3 -m venv .venv / source .venv/bin/activate / deactivate Classic: create / enter / leave a virtual environment by hand
    pip install -r requirements.txt / pip freeze > requirements.txt Classic: install from / write the frozen list (uv sync / uv.lock do this)
